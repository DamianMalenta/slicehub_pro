# Sesja AI — BI P&L Engine (`BiEngine`)

## Cel

Wdrożyć moduł BI (P&L) z agregacją w groszach (INT): przychód netto ze sprzedaży, COGS z dokumentów WZ (wiele WZ na zamówienie), koszty pracy z `sh_payroll_ledger`, OPEX z linii KSeF typu EXPENSE; cienki endpoint API oraz UI w `modules/bi/`.

## Pliki dotknięte

- `core/BiEngine.php` — nowy silnik `generateDashboard`
- `api/bi/dashboard_data.php` — wrapper HTTP + RBAC owner/admin/manager
- `modules/bi/index.html` — dashboard (prezentacja PLN = minor / 100)
- `modules/hub/index.html` — link do modułu BI
- `tests/test_runner.html` — test integracyjny T62
- `AGENTS.md` — liczba testów 62

## Decyzje architektoniczne

- **Net sales:** `SUM(grand_total) − SUM(sh_order_lines.vat_amount)` dla `sh_orders.status = 'completed'` w oknie `updated_at` (nagłówek nie ma `vat_amount`).
- **COGS:** suma `SUM(ROUND(line_net_value * 100))` po wszystkich liniach wszystkich dokumentów `wh_documents.type = 'WZ'` powiązanych z tymi zamówieniami; bez `MIN(id)` / `LIMIT 1`.
- **OPEX:** tylko `sh_ksef_invoice_lines.line_type = 'EXPENSE'` i faktury `status = 'accepted'`, okres po `COALESCE(processed_at, updated_at)` — uniknięcie podwójnego liczenia z magazynem (PZ/INVENTORY).
- **PDO:** unikalne nazwy parametrów w każdym prepared statement (ograniczenie sterownika).

## Otwarte pytania

- Czy raport sprzedaży ma w przyszłości używać osobnej daty „zaksięgowania” (np. zamknięcie fiskalne) zamiast `sh_orders.updated_at`?
- Czy OPEX ma uwzględniać faktury odrzucone po akceptacji (korekty) — obecnie tylko accepted + EXPENSE.
