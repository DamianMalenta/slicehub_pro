# A-002-B — Nawigacja administratora do Wszczepu

Realizacja zatwierdzonego Etapu A i jawnej kontynuacji właściciela. Stan: [CURRENT_STATE](../CURRENT_STATE.md). Bridge i baseline v1 pozostają bez zmian.

## Cel i UI
Kafelek „Symbiont — integracja” w sekcji Administracja Huba korzysta z istniejącego data-roles=owner,admin,manager. Prowadzi względnym linkiem do modules/symbiont/index.html?from=hub, bez tokenów i bez przekierowania do obcego origin. Widok Wszczepu oferuje powrót do Huba, gdy otwarto go z tego kafelka.

## Backend i bezpieczeństwo
Ukrywanie kafelka jest UX, nie autoryzacją. Nie zmieniamy login.php ani uprawnień domeny. JWT i localStorage Huba nie są przekazywane do Wszczepu. admin.php nadal wymaga odrębnego credentiala integracji; service token go nie zastępuje. Posiadanie roli w Hubie samo w sobie nie nadaje dostępu do diagnostyki B.

## Dwa znaczenia odłączenia
Kreator A zarządza lokalną rejestracją Mózgu i blokuje nowe diagnostyki. Nie zmienia SYMBIONT_BRIDGE_ENABLED, nie zatrzymuje PHP i nie usuwa danych. Panel B musi jasno wyjaśniać tę granicę. Włączenie/wyłączenie całego procesu hosta pozostaje konfiguracją administratora.

## Testy
Wykonać A2-T10 na rzeczywistym kodzie hub_app.js i HTML z izolowanym DOM/storage, bez odpalania tenant_config.php i rzeczywistego loginu. Sprawdzić widoczność dla owner/admin/manager oraz ukrycie dla waiter. Sprawdzić poprawny link i brak tokenu w adresie. Testy HTTP B muszą nadal odrzucać nieprawidłowy credential i token kanału service na admin.php.

Pilot pozostaje ograniczony routerem: nie odblokowujemy Huba lub tenant_config.php, żeby wykonać test nawigacji. Powrót do Huba jest ukryty w bezpośrednio otwartym pilocie. Produkcyjna walidacja sesji/ról i wizualny odbiór są oddzielnymi dowodami.
